# Технические решения

Документ дополняется по мере обсуждения. Принятые решения отделены от открытых вопросов; открытые вопросы не являются требованиями.

## Принято

- Проект предназначен для демонстрации в университете. Архитектура должна быть качественной, понятной и объяснимой, без избыточного усложнения.
- Бэкенд: C#, .NET 10 и ASP.NET Core. На текущей машине установлен SDK 10.0.204; при создании решения зафиксировать совместимый SDK в `global.json`.
- Архитектура бэкенда обязательно строится по принципам Domain-Driven Design (DDD), с разделением Domain, Application, Infrastructure и API.
- DDD соразмерен небольшой предметной области: архитектура не должна требовать искусственно сложной бизнес-логики ради демонстрации подхода.
- Фронтенд: React, TypeScript в строгом режиме и Vite; npm с lock-файлом. Конкретные совместимые версии пакетов фиксируются при создании приложения.
- Продуктовые рамки (локальный запуск, один пользователь, ручной ввод) и визуальные требования (минимализм, украинский язык, светлая тема, компьютер) — в `business-decisions.md`.
- Архитектура фронтенда свободная: при выборе учитываются скорость разработки и качество интерфейса.
- Десктоп-клиент: .NET MAUI, только Windows, нативные контролы на XAML без Blazor Hybrid. Повторяет экраны и дизайн React-версии; React-версия в `frontend/` остаётся и продолжает работать (issue #31).

## Архитектура и правила реализации

- Один бэкенд с разделением ответственности: Domain (модель и бизнес-правила), Application (сценарии), Infrastructure (хранение данных), API (HTTP-интерфейс для React).
- Доменная модель не зависит от React, HTTP и конкретной базы данных.
- Одна предметная область — учёт расходов. `Expense` и `Category` — отдельные небольшие агрегаты; расход ссылается на категорию по идентификатору. Объект-значение суммы инкапсулирует точность и допустимость денежного значения. Не создавать агрегат «месяц», хранящий все расходы: месячная статистика — результат запроса.
- Для MVP не предполагаются микросервисы, брокеры сообщений и Event Sourcing: текущие сценарии не обосновывают их необходимость.

### Зависимости и обязанности

- `Domain`: сущности, инварианты, методы изменения состояния. Без ASP.NET Core, EF Core, DTO транспорта и внешних сервисов. Не допускать изменения инвариантов через публичные setters.
- `Application` зависит от `Domain`: сценарии работы, координация агрегатов, интерфейсы хранения, границы транзакций. Например, проверка доступности выбранной категории перед созданием расхода принадлежит сценарию; доменная модель категории определяет её активность.
- `Infrastructure` зависит от `Application` и `Domain`: EF Core (Npgsql), PostgreSQL, конфигурация маппинга, миграции и реализации интерфейсов.
- `API` вызывает сценарии Application; Infrastructure подключается в точке настройки зависимостей. Обработчики HTTP не содержат расчёты и бизнес-правила. Сущности и `DbContext` не возвращаются клиенту.
- Простые сервисы сценариев и явное внедрение зависимостей. Не добавлять MediatR, generic repository, универсальные базовые классы и доменные события без конкретной потребности. EF Core уже предоставляет механизм отслеживания изменений; дополнительная обёртка над каждой его операцией не нужна.
- Чтение статистики выполняется агрегацией в SQL через репозиторий расходов (`IExpenseRepository`), без загрузки всех агрегатов; отдельного слоя запросов нет. Одно действие пользователя сохраняется атомарно.

### Хранение, деньги и даты

- PostgreSQL; EF Core (Npgsql) с миграциями.
- Всё приложение (PostgreSQL, API, фронтенд) собирается и запускается через Docker Compose одной командой. Для разработки допустимо запускать API и фронтенд локально, а PostgreSQL — из Compose.
- Данные PostgreSQL хранятся в именованном Docker-томе, не в Git. Строка подключения задаётся переменными окружения; пароли — в `.env`, в Git только `.env.example`. Тесты используют отдельные временные базы. Не удалять том и не пересоздавать пользовательскую базу ради обновления схемы (`docker compose down -v` — только по явному запросу).
- Валюта только UAH. В домене денежные операции используют `decimal`, в PostgreSQL суммы хранятся как `numeric(12,2)`. Не использовать `float`/`double` для денежных расчётов.
- Сумма расхода положительная, не более двух знаков после запятой. Лишнюю точность отвергать, не округлять молча. API принимает/отдаёт денежные значения точными десятичными строками; на фронтенде не выполнять финансовые расчёты через двоичную дробную арифметику. Итоги считает бэкенд; форматирование отделено от расчёта.
- Дата расхода — календарный `DateOnly`, в API формат `YYYY-MM-DD`, без преобразования в UTC. Месяц фильтруется как интервал от первого дня включительно до первого дня следующего месяца исключительно.
- В технических timestamps допустим UTC. «Сегодня» для расхода — локальная календарная дата пользователя; не заменять её UTC-датой.
- Архивирование категории не удаляет расходы и не исключает их из статистики. Добавление нового расхода в архивную категорию запрещено. Существующий расход в архивной категории можно изменять и переносить в активную категорию (см. `business-decisions.md`).

### API и фронтенд

- HTTP JSON API, явные DTO, единообразные ошибки через Problem Details, OpenAPI для демонстрации и проверки контракта. Не выдавать внутренние исключения и финансовые данные в диагностические логи.
- Проверять входные данные на границе API, а доменные инварианты — внутри модели; клиентская валидация служит удобству и не заменяет серверную.
- React организуется по функциям приложения: расходы, категории, обзор. Общие UI-компоненты выделяются по реальному повторному использованию. Не нужен сложный глобальный store для нескольких форм и фильтров.
- Одна светлая палитра, согласованные отступы, типографика и повторно используемые элементы. Не заполнять экран декоративными блоками без функции.
- Украинские подписи и форматирование `uk-UA`; обязательны понятные пустые состояния, ошибки, состояние загрузки и обратная связь при сохранении.
- Семантические элементы, подписи полей, видимый клавиатурный фокус, достаточный контраст. Анимации короткие и учитывают `prefers-reduced-motion`.
- При создании проекта использовать существующие зависимости; новые библиотеки добавлять, когда они сокращают реальную сложность. Конкретную библиотеку графиков и компонентов выбрать на этапе UI, не перекладывая обычный технический выбор на пользователя.

### Визуальная система и оболочка фронтенда

- Направление — «стандарт категории»: привычный финтех-кабинет с боковым меню, белой областью содержимого и одним синим акцентом. Выбрано через скилл `impeccable`; продуктовый контекст — в `PRODUCT.md`, описание системы — в `DESIGN.md`.
- Токены — CSS-переменные в `frontend/src/styles/tokens.css`. Компоненты берут цвета, отступы, размеры шрифта и скругления только из токенов.
- Палитра: поверхность `#ffffff`, вторая поверхность (меню) `#f4f7fa`, текст `#151b24`, приглушённый текст `#545b66`, границы `#dfe3e8` и `#818a95` (поля), акцент `#1f5ed9`, ошибки `#c51e21`. Акцент отмечает основное действие, текущий раздел, фокус и ссылки; его светлый тон — выделение текста. Для украшения акцент не используется.
- Контраст проверен расчётом: текст и подсказки — не ниже 4.5:1, границы полей и обводка фокуса — не ниже 3:1.
- Типографика: Inter Variable, подключён локально пакетом `@fontsource-variable/inter` и не требует интернета. Размеры 14 / 16 / 20 / 24 px и 36 px (`--font-size-display`) только для итога месяца на «Огляді», насыщенность 400 / 500 / 600. Поля ввода используют табличные цифры через токен `--numeric-figures`; тот же токен применять при выводе денежных сумм и дат.
- Отступы — шкала с шагом 4 px: 4, 8, 12, 16, 24, 32, 40, 48. Скругления: 6 px у элементов управления, 10 px у панелей. Высота элементов управления — 40 px.
- Оболочка `AppShell`: меню шириной 248 px и колонка содержимого до 960 px. Минимальная ширина окна — 960 px. Маршруты (`react-router`): `/` — «Огляд», `/expenses` — «Витрати», `/categories` — «Категорії»; неизвестный адрес показывает страницу «не найдено».
- Базовые компоненты собственные, в `frontend/src/ui/`: `Button`, `TextField`, `Select`, `LoadingState`, `EmptyState`, `ErrorState`, `PageHeader`. Сторонняя библиотека компонентов не используется. Иконки — `lucide-react`. Стили — CSS Modules рядом с компонентом.
- Движение отмечает только смену состояния: переходы длятся 150–180 мс, выделенные анимации — плашка текущего раздела в меню, появление уведомления и проявление кольца долей на «Огляді». Новое содержимое проявляется без движения по экрану: страница при смене раздела (с подъёмом на 4 px), встроенные формы и подтверждения, состояния «пусто» и «ошибка», текст ошибки у поля. Индикаторы загрузки (вращение в кнопке, мерцание заглушек) зациклены. При `prefers-reduced-motion: reduce` все анимации и переходы отключены.
- Клавиатурный фокус — обводка 2 px акцентным цветом у всех интерактивных элементов. Первая клавиша Tab открывает ссылку «Перейти до вмісту» мимо меню. После закрытия встроенной формы фокус возвращается на кнопку, которая её открыла; после удаления строки — на соседнюю строку.
- Справочная страница компонентов `/ui` доступна только в режиме разработки и не попадает в production-сборку.
- Графики: библиотека не используется. Единственный график — кольцо долей категорий — собственный SVG-компонент `CategoryBreakdown`; библиотека не сократила бы сложность и добавила бы вес сборки. Не больше 6 сегментов: при большем числе категорий пять крупнейших показаны отдельно, остальные объединены в «Інші»; в таблице остаются все категории. Цвета — токены `--chart-1`…`--chart-6`, проверены на различимость, в том числе при нарушениях цветового зрения; точные значения всегда есть в таблице рядом. Доли рисуются из процентов бэкенда, деньги на фронтенде не пересчитываются.
- Выбранный месяц общий для «Огляду» и «Витрат» (`MonthProvider`); сумма вводится и хранится как десятичная строка, форматируется `Intl.NumberFormat('uk-UA')` прямо из строки.
- Версии пакетов фронтенда зафиксированы в `frontend/package-lock.json`.

### Фундамент бэкенда

- Структура: `backend/Finstat.slnx`, проекты `backend/src/Finstat.{Domain,Application,Infrastructure,Api}`. Версии пакетов — централизованно в `backend/Directory.Packages.props`.
- Контроллеры (`[ApiController]`, папка `Controllers/`). Бизнес-эндпоинты — под префиксом `/api`; проверка состояния — `/health` (включая доступность БД).
- Имя файла и типа несёт роль: `CategoryEntity`, `CategoryRequestDto`, `CategoryResponseDto`, `CategoryService`, `CategoriesController`.
- Папки внутри проектов по роли, namespace = папка: Domain — `Entities/`, `Results/`; Application — `Services/`, `DTOs/`, `Repositories/`; Infrastructure — `Repositories/`, `Configurations/`; Api — `Controllers/`, `Helpers/`.
- Ошибки: Result pattern (`Domain/Results`): домен и сервисы возвращают `Result` / `Result<T>` с ошибкой `Validation` или `NotFound`, исключения для бизнес-правил не используются; контроллер (`AppControllerBase.Failure`) превращает `Validation` в 400, `NotFound` в 404 (Problem Details); необработанные исключения — 500 без внутренних деталей.
- OpenAPI и Swagger UI доступны только в окружении Development.
- Миграции применяются автоматически при старте API (один локальный экземпляр, запуск одной командой). Новые миграции создаются локальным инструментом `dotnet-ef`; команда — в README.
- Строка подключения — `ConnectionStrings:Finstat` (переменная `ConnectionStrings__Finstat`). В Compose собирается из `.env`; при локальном запуске API — через `dotnet user-secrets`.
- CORS не нужен: фронтенд в разработке ходит к API через прокси Vite, в Compose — через тот же origin. Десктоп-клиент обращается к API напрямую, но CORS — механизм браузера, нативный `HttpClient` его не применяет, поэтому на бэкенде CORS не включается и контракт не меняется.
- Фронтенд в Compose — сервис `web`: multi-stage `frontend/Dockerfile` (сборка на Node 22, раздача статики nginx). nginx отдаёт `index.html` для адресов приложения и проксирует `/api/` на сервис `api`. Порт хоста — `WEB_PORT` (по умолчанию 3000).
- Хранение: интерфейс репозитория на каждый агрегат объявляется в Application и реализуется в Infrastructure; `SaveChanges` DbContext — граница транзакции одного действия пользователя. Общие базовые репозитории и Unit of Work не вводятся до реальной потребности.
- CI не настраивается: проверки выполняются локально.
- Комментариев в коде нет: ни в исходниках, ни в конфигурации (Dockerfile, Compose, `.env.example`). Пояснения — в README и этих документах. Исключение — файлы, сгенерированные инструментами (миграции EF Core), их не правят вручную.

### Десктоп-клиент (MAUI)

- Структура: `desktop/Finstat.Desktop.slnx`; `src/Finstat.Desktop.Core` (net10.0) — `DTOs/`, `Api/`, `Formatting/`, `ViewModels/` без зависимости от MAUI; `src/Finstat.Desktop` (net10.0-windows10.0.19041.0, без упаковки MSIX, `WindowsPackageType=None`) — `MainPage`, `Views/`, `Controls/`, `Resources/`; `tests/Finstat.Desktop.Tests` — xUnit v3 на Microsoft Testing Platform. Общие настройки и пакеты — `desktop/Directory.Build.props` и `desktop/Directory.Packages.props`, SDK — `desktop/global.json`.
- MVVM без сторонних пакетов: `ViewModelBase` (`INotifyPropertyChanged`), `AsyncCommand`, компилируемые привязки (`x:DataType`). Зависимости регистрируются в `MauiProgram`. Выбранный месяц общий для «Огляду» и «Витрат» (`MonthState`), как `MonthProvider` в React.
- Клиент API — `FinstatApiClient` на `HttpClient`, те же DTO и маршруты, что у React-версии. Адрес — `http://localhost:8080/`, переопределяется переменной окружения `FINSTAT_API_URL`. Ошибки: `detail` из Problem Details, при недоступном сервере — украинское сообщение о соединении.
- Деньги: суммы и доли приходят строками, клиент их только форматирует (`decimal`, культура `uk-UA`, формат `N2` + «грн»). `float`/`double` для денег не используются; итоги и доли не пересчитываются. Введённая сумма проверяется по тем же правилам и с теми же сообщениями, что в React, и уходит строкой.
- Дизайн повторяет токены `frontend/src/styles/tokens.css` в `Resources/Styles/Colors.xaml` и `Styles.xaml`: те же цвета, размеры шрифта 14 / 16 / 20 / 24 / 36, межстрочный интервал 1.5 (1.25 у заголовков), отступы, скругления 6 / 10 px, высота элементов 40 px, меню 248 px. Колонка содержимого центрируется в области справа от меню и растягивается вместе с окном до 1200 px (с отступами 48 px; `WidthRequest` выставляется из `MainPage.OnContentSizeChanged`); колонки таблиц — гибкие, без фиксированной ширины всей таблицы, чтобы ничего не обрезалось при минимальном окне 1100 px. Шрифт Inter (OFL) лежит в `Resources/Fonts` вместе с лицензией. Иконки — SVG, сгенерированные из данных `lucide-react`.
- Кольцо долей — собственный `GraphicsView` (`Controls/DonutChart`) с геометрией SVG из React (r = 80 и обводка 22 в системе 200 × 200, промежутки между сегментами, не больше 6 сегментов, «Інші»); подсветка сегмента и строки таблицы при наведении.
- Движение (`Controls/Motion`, `Controls/MotionBehaviors`) повторяет веб: переходы 150 мс (`Fast`) и 180 мс (`Base`), кольцо долей проявляется 600 мс, затухание `Easing.CubicOut` (ближайший встроенный аналог `cubic-bezier(0.16, 1, 0.3, 1)`). При смене раздела новый раздел (с фоном страницы, поверх старого) проявляется за 180 мс с подъёмом на 4 px, а старый остаётся непрозрачным и скрывается, когда новый достиг 1, поэтому яркость при переходе не проседает (если страница была прокручена, старый раздел остаётся визуально на месте и гаснет за 180 мс; при быстром возврате в ещё не скрытый раздел он сразу ложится сверху непрозрачным, а полупрозрачный уходящий гаснет за 150 мс); сначала новый раздел один кадр раскладывается невидимым (иначе пересчёт макета съедает начало анимации), прокрутка возвращается наверх (старый раздел при этом визуально остаётся на месте), фокус переходит на активный пункт меню, значки пункта плавно меняются местами; плашка текущего раздела в меню скользит между пунктами; наведение на пункт меню, строку таблицы «Огляду» и сегмент кольца плавно меняет цвет и прозрачность (сегмент при наведении утолщается на 3 px, остальные притухают); уведомление появляется и исчезает со сдвигом на 8 px; кольцо долей «разворачивается», когда данные появились после загрузки, пустого месяца или смены месяца (`OverviewView` по переходу `IsReady` в true), но не при тихом обновлении; возврат в уже загруженные «Огляд» и «Витрати» обновляет данные без состояния загрузки (`RefreshAsync`; ответ устаревшего запроса отбрасывается по номеру загрузки), а при ошибке показывается состояние ошибки; состояния «пусто» и «ошибка», встроенные формы, подтверждения и тексты ошибок проявляются через `RevealBehavior` без движения по экрану. Пункт меню — `Grid` со слоем наведения (`BoxView` с `Opacity`, под текстом) и прозрачной `Button` сверху: кнопка даёт Tab, Enter/Space, видимый фокус и роль для Narrator, а стиль `NavButton` держит фон прозрачным во всех состояниях `VisualStateManager`, поэтому единственный автор наведения — анимируемый слой. Родной `PointerOver` кнопки WinUI вместе с обработчиком указателя, красившим её фон, вызывал мерцание. Эквивалент `prefers-reduced-motion` — `UISettings.AnimationsEnabled` в Windows, читается в одном месте (`Motion.Enabled`); при `false` все состояния применяются мгновенно. Hover у кнопок остаётся на состояниях `VisualStateManager` (мгновенный).
- Фокус с клавиатуры показывается системной рамкой WinUI, а не 2 px акцентной обводкой веба: это осознанное отличие, оно совпадает с остальными кнопками десктопа.
- Особенности Windows: `Picker.Title` выводится как подсказка внутри поля, а не заголовком над ним; родная иконка `CalendarDatePicker` скрыта, вместо неё иконка lucide, как в React. Обе правки — маппинги хендлеров в `MauiProgram`.
- Проверено по скриншотам рядом с React-версией (`docs/screenshots/desktop-*.png`): размеры карточек, строк таблиц и кольца совпадают с вебом с точностью до 1–2 px.
- Запуск и проверки — README, разделы «Локальная разработка» и «Проверки».

### Проверки

- Бэкенд: автотестов нет (тестовый проект удалён по решению владельца, 2026-11-24); проверка — сборка без предупреждений и ручная проверка API.
- Фронтенд: typecheck, lint, build; Vitest и React Testing Library для существенного поведения. Браузерные сценарии добавлять по необходимости, преимущественно для ключевого пути ввода расхода и обновления статистики.
- Десктоп-клиент: `dotnet build` без предупреждений и `dotnet test` из `desktop/` — форматирование и разбор сумм, клиент API на подставном `HttpMessageHandler` (Problem Details, недоступный сервер), сценарии: ввод расхода обновляет список и «Огляд», неверный ввод не отправляется, расход в другом месяце переключает месяц, смена месяца перезагружает статистику, редактирование расхода в архивной категории. Визуальная проверка — запуск против `docker compose up` и сверка со скриншотами React-версии.
- Сквозной тест (`frontend/e2e`, Playwright, `npm run test:e2e`) — сознательное исключение из правила об отдельных базах: он работает против запущенного `docker compose up` и его базы, потому что проверяет именно сохранность данных в томе после пересоздания контейнеров `db` и `api`. Тест добавляет один расход с меткой `E2E-finstat` в комментарии и удаляет его в конце; после сбоя удаляются оставшиеся расходы с этой меткой за текущий месяц. Другие данные он не меняет.
- При создании решения оформить реальные команды запуска и проверок в README и package scripts. До появления конфигурации не считать предлагаемые команды уже существующими.
- Для UI дополнительно проверять отрисованный результат, для миграций — сохранность существующих данных. Объём проверки соответствует изменению; не вводить произвольную цель покрытия тестами.

## Работа с Git

- Хостинг — приватный репозиторий GitHub `shpvk/finstat`; разработка ведётся вдвоём.
- Основная ветка — `Development`. Рабочие ветки создаются от неё; прямой push в неё запрещён. Интеграция — через pull request.
- Имена веток и коммиты — на английском. Сообщение коммита — одна строка, обычно 1–3 слова, максимум 5, без тела.
- Подготовка реализации, независимое ревью и тестирование завершаются до публикации. Публикация и слияние — отдельные действия по запросу пользователя.
